# Project Claude Code instructions

This is the project-level Claude Code instruction file. Claude Code composes instructions from the
enterprise, user, project, and subdirectory levels; nearer subdirectory instructions refine the
project rules for their subtree. This file supplies the project-level configuration and does not
override enterprise or user policy.

Follow [AGENTS.md](AGENTS.md) for the repository's content, security, test, and commit rules. Read
[BLUEPRINT.md](BLUEPRINT.md) before changing study material. Keep lab tests keyless, use Python
3.11+ standard-library-first code, and run `ruff check .`, `ruff format --check .`, and `pytest -q`
after changes.

Claude Opus 5, acting as the orchestrator in Claude Code, may run `git add` and `git commit`, and
only after the full gate set passes. The permission is scoped to that model in that role: every
delegated implementer — Codex, Antigravity, or any other CLI — leaves its work uncommitted in the
working tree for the orchestrator to review, re-gate, and commit. [AGENTS.md](AGENTS.md) no longer
states the older blanket prohibition, so this paragraph is the only rule on the subject rather than
an override of a conflicting one.

Use `/verify-triage` to run the triage verification sequence. Use the `triage-security` skill when
reviewing the untrusted-input boundary, secret handling, or tool permissions.

The active feature is `003-claude-code-domain`. For the technologies in use, the project structure,
and the shell commands that verify a change, read [the implementation
plan](specs/003-claude-code-domain/plan.md) and [its
quickstart](specs/003-claude-code-domain/quickstart.md). Feature 002's
[plan](specs/002-lab-runner-mock-exam/plan.md) describes the lab runner and the mock exam, and
feature 001's [plan](specs/001-study-site-foundation/plan.md) still describes the site's
foundation.

The site is an Astro 7 and TypeScript project in `site/`, rendering this repository's existing
markdown in place — copying study text into `site/` fails the build. Exam figures come from
`site/src/data/blueprint.json`, generated from `BLUEPRINT.md` by `tools/export_site_data.py`; never
edit that file or type a weight by hand. The same rule now covers `site/src/data/mock.json` and
`site/src/data/items.json`, generated by `tools/export_mock_data.py` and
`tools/export_item_bank.py`.

Pyodide runs `lab/` and `drills/` in a Web Worker on lab pages only, fetched after an explicit Run
and never before; the mock exam and the quizzes are plain TypeScript over build-time data and must
never import the runtime client. Per-domain quotas come from `drills.engine.mock.apportion_items` at
build time — never reimplement apportionment in TypeScript. Practice items live in `drills/bank/`
and must be original, validated by `python -m drills.engine validate`.

The Claude Code module adds `site/src/data/claude-code.json`, generated by
`tools/export_claude_code_data.py` from `claude-code/commands.yml`, this repository's own `.claude/`
directory, and a recording of what its hook actually decides — never hand-edit it, and never write a
sentence in `site/` describing what that hook denies. Only the configuration builder may reach the
runtime client, through a `run-hook` message whose exit code is a decision: a hook exiting `2` is
the hook working, not a failure. The instruction hierarchy is concatenated root-down, never
overridden, and terminal transcripts are never written to the candidate's device.
